# Arthas 方法诊断

## 接入前提

Arthas 必须加载到目标 JVM，不能仅凭远程方法名工作。首期在 Docker 场景通过已授权的目标会话执行 `docker exec`，定位 Java 进程并启动或连接固定版本 Arthas。

不默认 Java PID 为 1，也不默认镜像具备 JDK attach 能力、可写目录或外网访问。需验证 JVM 用户、启动参数、镜像和实际 Java 版本。

工具包可镜像预置。0.3.8 接入时检查完整包和 arthas-boot.jar；缺少启动器时从 Maven Central 下载固定版本 4.0.5 的官方可执行启动 JAR并校验 SHA-256。仅boot JAR模式通过官方启动器自动下载解压所需依赖，不需要系统 unzip 或 JDK jar 命令。当前仓库不内置 Arthas 二进制包，不自动安装系统工具或上传文件。

## 方法搜索

0.3.13起，容器发布重建或重启后，在原SSH连接仍正常且目标服务器未变时，依次点击“发现JVM”→选择Java进程→“接入Arthas”→重新搜索方法即可，无需重新登录堡垒机。发现时按容器ID、容器启动时间和进程启动标识淘汰旧接入，即使PID相同也不能复用；旧方法/ClassLoader和多层范围会清空，需要重新搜索核对。历史结果保留，但失效JVM的“继续诊断”不可用。

输入方法名或 `ClassName#methodName`，在选定实例的已加载业务类中搜索。候选展示完整类名、签名、ClassLoader 和实例来源。

同名方法、类未加载以及不同节点运行不同版本必须如实说明。选择某个重载签名不代表 Arthas 命令天然只增强该重载，应按实际命令能力显示匹配范围。

## 快捷模板

0.3.14默认使用“深入追踪（单次请求）”，适合一次请求很慢、希望减少重复业务执行的场景。它与下面的精确trace模板分别提供采样线索和已增强方法的调用计时。

CLASS 和 METHOD 为占位符，选择候选后再生成真实命令。

| 入口         | 示例                                                   |
| ------------ | ------------------------------------------------------ |
| 慢调用       | `trace CLASS METHOD '#cost > 200' -n 5`                |
| 参数与返回值 | `watch CLASS METHOD '{params,returnObj}' -s -x 2 -n 5` |
| 异常调用     | `watch CLASS METHOD '{params,throwExp}' -e -x 2 -n 5`  |
| 是否进入     | `watch CLASS METHOD 'params' -b -x 1 -n 5`             |
| 调用统计     | `monitor -c 5 CLASS METHOD`                            |
| 调用来源     | `stack CLASS METHOD -n 5`                              |
| JVM 概况     | `dashboard`                                            |
| 繁忙线程     | `thread -n 5`                                          |
| 阻塞线程     | `thread -b`                                            |

monitor 的 `-c` 是统计周期，ClassLoader 使用 `--classloader`；trace/watch 的 `-c` 语义不同，不能采用统一参数拼接。参数和返回值观察应按需选择字段，不默认持久化完整业务对象。

## 多实例执行

每个实例先核对真实容器、JVM 和方法，再单独提交任务。界面区分已提交、增强完成、等待调用、已有结果和失败，不能把一个节点成功展示为全部节点成功。

trace 主要输出当前增强方法的一层直接调用耗时，可继续诊断慢的下一层方法。异步线程和跨 RPC 不会自动形成完整链路；未采集的历史调用无法事后补出。

## 数据通道

优先验证现有 SSH/PTY 和官方客户端的文本输出，先保证可用。若 agent HTTP API 实际可达，可使用结构化结果。

SSH 端口转发到宿主机不等于能访问容器内的 127.0.0.1。需要验证真实网络路径，不能默认开放新公网端口。Tunnel 是已加载 agent 的连接转发，不是 attach 工具，也不能直接假定它代理任意 HTTP API。

## 停止与异常

HTTP API 长任务使用 `init_session → async_exec → pull_results`，停止用 `interrupt_job`，最后 `close_session`。终端通道按实际客户端验证中断行为。

不使用全局 `stop` 或 `reset` 假装停止当前任务，以免影响其他连接。Starter 默认禁用 stop 的行为也需要纳入兼容验证。

`-n` 是采集次数条件，不是无调用超时。工具侧任务结束时间仍需要发送中断；APP 被强杀时，本地计时器不会继续工作。未实现并验证远端终止机制时，掉线只能显示未知状态并在重连后核对，不能宣称一定已停止。

## 当前状态

0.3.0 已实现容器内 JVM 发现（不假定 PID=1）、预置完整 Arthas 4.0.5 包探测及 attach、按业务包/完整类名搜索已加载方法、ClassLoader 候选、trace/watch/异常/monitor/stack 预览与执行、独立任务原始结果和停止。

默认目录为 /tmp/tracelogdock-arthas-4.0.5，可填写现有预置目录。APP 以 JVM UID 执行下载、Java/curl；需要 sh、awk、readlink、curl、Linux /proc 和可 attach 的 Java。已有完整包不重新下载，版本不符时提示更换目录，不覆盖可用版本。

自动下载启动 JAR需要 sha256sum、mktemp 等常见 shell 工具、目录写权限和 Maven Central HTTPS 出网；已有同版本 arthas-boot.jar 可以跳过JAR下载。仅boot模式设置 `--use-version 4.0.5 --repo-mirror center`，通过官方Arthas HTTPS下载接口获取依赖并由Java解压，不选择latest、不切换HTTP。依赖保存在所填目录下的 `.arthas/lib/4.0.5/arthas`；已有缓存由官方启动器复用。启动JAR与完整发行包是两种入口，不把boot JAR误当成完整包使用 `--arthas-home`。

启动JAR下载最长120秒，JAR安装与官方启动器准备/接入命令分别最长150秒；普通完整包接入保持原命令超时。失败显示远端错误，可检查容器HTTPS出网与写权限后重试。JAR下载完成后及启动器执行后重新核对目标身份与工作区状态，最终还通过HTTP version/session验证版本/PID才登记成功。默认 /tmp 目录可能随容器重建或临时文件清理而丢失，下次接入会重新检查。

官方可执行启动JAR地址为 `https://repo.maven.apache.org/maven2/com/taobao/arthas/arthas-boot/4.0.5/arthas-boot-4.0.5-jar-with-dependencies.jar`，固定 SHA-256 为 `5a967356d04db1bf34237dfe5419b67fcea80d4bc47c6b70c466883561d4ac85`。未带classifier的同名Maven JAR不含可执行Main-Class，不能用于 `java -jar`。依赖包由官方启动器通过HTTPS下载；APP不宣称校验了其ZIP哈希。第三方许可见[组件说明](../THIRD_PARTY_NOTICES.md)。

命令不读取进程完整参数。HTTP及Telnet仅绑定容器内127.0.0.1。Arthas4.0.5启动器即使带--attach-only也先做Telnet探测，--telnet-port -1会抛出port out of range；0.3.9改用--telnet-port 0分配随机本地端口，避免负端口错误与固定端口冲突；界面诊断仍使用HTTP；既有 agent 版本/端口冲突时须人工核对，不停止其他客户端 agent。

最长运行时间由 APP 计时器请求中断；掉线、退出或清理失败显示未知，重连后不自动重放诊断。各实例分别接入、搜索和执行，不提供未经逐实例核对的批量增强。结果仅在内存展示，每任务保留最近200条；trace已提供耗时解析和继续诊断入口；离线文件上传仍待实现。

目前通过本机 shell 安装脚本、隔离 SSH/HTTP 协议与实际 Electron 流程验证。真实 Docker 引擎、JVM attach 和实际 JumpServer 版本尚未完成兼容验收，不能据模拟响应声称已增强生产 JVM。

## 耗时解析与继续诊断

0.3.10将trace原始调用树转换为耗时表，按累计耗时降序显示方法、占总耗时比例、调用次数和调用方源码行号。方法节点cost/totalCost以纳秒换算为秒/毫秒；重复调用使用totalCost，不把最后一次cost当累计值。增强结果effect.cost不算业务调用耗时，父子调用包含关系不能相加，代理包装节点不参与耗时排行。多次采集分别展示，原始JSON保留在折叠项，其他诊断模板继续显示原始结果。

点击调用行“继续诊断”，会回到该任务的实例/JVM，查找已加载方法并填写完整类名、方法及真实ClassLoader，保留当前阈值/采集次数/最长时间，定位参数区。线程上下文ClassLoader不用于推断子调用加载器。唯一具体候选自动选中；存在重载或多个ClassLoader时需选择。接口/抽象方法会搜索同包（含子包）的同名具体实现供选择，不猜测实现；abstract/native方法不可选。SpringCGLIB代理调用优先搜索去掉代理后缀的原始类。

该入口只准备下一步，点击“执行诊断”后才启动新任务，并需重新触发业务。原JVM连接失效时入口禁用；有活动任务时仍按现有规则先停止当前任务才能执行。新任务在前、旧任务默认收起，也可点击“回到诊断参数”，避免在长历史中反复滚动。

## 一次入口请求的多层追踪

0.3.12新增“多层追踪”。先搜索并选择最外层原始实现入口（如Controller导出方法），再选择该模式，默认采集1次、最长300秒，可按需调整。入口会固定显示；搜索其他类的候选并加入范围时，入口不会跟着改变，必要时可点击“将当前候选设为入口”。

追踪类每行填写一个完整类名，追踪方法名按逗号或换行分隔。可点击“加入当前候选”，再用“列出当前类方法”查看同一ClassLoader中可增强的具体方法，勾选私有辅助方法。也可加入当前JVM/加载器对应的历史诊断方法。方法名应用于整个类列表，因此每个类内匹配该名称的重载均属于实际范围。

点击“核对追踪范围”，APP使用当前JVM、入口ClassLoader查询真实方法，排除构造器/abstract/native，列出全部实际匹配。修改类、方法、入口或加载器会使预览失效。核对后点击执行，再触发一次业务，即可在同一结果里看到所选范围内多层调用及其直接子调用。

命令通过trace -E生成，类名/方法名来自明确输入和已核对元数据，不接受任意正则/任意命令。实际增强排除未列出的派生类，执行前再次核对完整范围，包含所有匹配重载；范围变化时不执行增强。一个任务只使用同一ClassLoader、同一实例/JVM及独立HTTP会话，沿用已有停止和超时机制。

Arthas4.0.5嵌套增强的条件计时器与原始树耗时不是同一口径，多层模式不使用#cost阈值，而在采集后按真实节点totalCost排序。输出条件固定最外层入口类/方法，避免无关接口单独调用辅助方法时消耗采样。所选范围中不要加入该入口更上层的方法；如需从Controller一路观察Service/Assembler，应将Controller设为入口。该模式不会自动无限展开所有代码，也不跨异步线程或RPC自动串联。

## 单次请求的自动深入追踪

选择Controller等同步入口后，使用“深入追踪（单次请求）”，点击执行并等待增强完成，再触发一次业务。无需输入任何下游类或方法范围，也不需要逐层重新导出。任务启动后捕获首个进入的同名入口调用（包括同名重载）；并发流量下可能先捕获其他用户的同名请求，界面显示实际线程。只观察所选ClassLoader中的明确入口类，排除额外子类增强。

APP使用入口watch的进入/退出事件绑定线程与目标JVM单调时钟，在该线程执行期间调用thread读取完整堆栈，并用只读OGNL获取目标JVM采样后时钟；入口结束时剔除结束之后的样本，避免线程池连续执行同名请求时混入后续调用。业务私有方法、深层辅助类、数据库驱动、JDK等待栈均无需预先增强。默认目标采样间隔1000ms（可选500/2000ms）、最长600秒（包含等待入口的时间），界面实时展示证据，无需等请求完成。Arthas4.0.5无事件的HTTP轮询最多等待约2秒，再叠加SSH及目标响应会延长实际间隔；界面如实显示平均间隔，不承诺固定每秒一次。

结果按完整路径统计样本，并列出业务帧的出现比例、最深业务帧样本数及源码位置。父子帧同时出现在一个样本中，不能相加；比例不是精确方法耗时或调用次数。入口总耗时独立使用目标JVM进入/退出nanoTime差计算，不使用watch的cost。聚合覆盖所有有效样本，原始结果仍仅保留最近200条；业务参数、返回值、异常内容不在入口表达式中读取。

锁阻塞可展示持锁线程ID；连接池借用、数据库驱动网络读写、一般网络、休眠和文件IO仅标注相应线索。RUNNABLE不直接判定CPU热点，数据库网络栈不直接断定缺索引/慢SQL/数据库锁。最常见路径优先展示，完整路径可以展开；只能给出采样覆盖到的证据，不能保证找到任意问题的最终根因。短暂方法可能漏采，也不追踪异步子线程或远端服务内部。

入口正常/异常退出后只中断并关闭本任务的专用HTTP会话，不发送全局stop/reset。并发线程和递归退出不会错误完成当前调用；不含入口的线程池后续栈不计入结果。停止诊断不会取消业务请求。手动停止或超时保留部分采样，断线/容器变化或未确认清理显示未知状态；强杀APP后仍需人工核对远端观察任务。此方案避免全业务包方法增强，但采样与入口增强仍有开销，当前未量化生产CPU影响。

## 简明诊断结论

0.3.15深入诊断默认只展示优先排查的方法、源码/调用位置、发现和优化建议。同方法的重复栈与行号变化合并，不重复列出全部父方法。建议根据数据库网络、连接池、锁、远端IO、休眠、文件IO或运行路径等实际证据生成；没有源码/SQL执行计划时不会直接断言缺索引或代码循环查询，改动建议明确使用条件。

采样表、线程信息和完整栈默认折叠到“查看诊断依据”，原始结果保持折叠。执行中仅显示正在诊断；无有效业务位置时不编造慢点。仅一个样本标记初步线索，不完整结果标记部分证据；出现次数不作为精确耗时。

## 独立配置与运行源码

0.3.17将模型配置移至左侧独立“AI 配置”，方法诊断采用接入/方法/结果三步。深入采样结束后可按任务原JVM与方法实际ClassLoader调用jad读取运行方法，无需本地项目，也不重执行导出；反编译片段与原始Java行号分开标识，Mapper XML不凭空补全。原任务源码缓存后可断线查看；容器重建时未缓存源码不绑定新JVM。详细流程见[源码与AI分析](ai-analysis.md)。
